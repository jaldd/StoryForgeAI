# 阶段 1 前半：质量门禁（quality-gate）- 需求

> 需求来源：`specs/ROADMAP.md` 1.1-1.4 条目（L116-148）。
> 最高约束：`.specify/memory/constitution.md`。
> 现状证据与详细设计见同目录 `design.md`；任务分解见 `tasks.md`。
> 拍板记录（2026-08-29）：阶段 1 拆两个 feature--先 `quality-gate`（1.1-1.4），后 `style-loop`（1.5-1.6）；词表/阈值用独立 JSON（与 0.2 写作铁律.md 分开）；打回机制定为**修复式打回**。开放问题 1/3 就此关闭。
> 评审修订（2026-08-29）：A12 拍死「任一不可定位即整文修复」（D12）；A18 删「缺失必备称呼」对齐 D10；A28 措辞对齐「双方现算」；A34 豁免路径拍死（强制定稿/人工确认直存）。

## 1. 背景与问题

阶段 0 修完地基后，质量问题仍不可度量、不可拦截：

1. **审核不可分维度**：reviewer 只返回 `{"pass", "reason", "issues"}`，六个审查维度混在一个结论里；打回意见是一坨文字，无法定位到句。
2. **打回即从零重写**：reviewer 不通过回 writer 整章重写--好稿陪葬、round 2 换新毛病。
3. **零确定性检查**：SKILL.md 的 8 条硬规则只在手工 Claude 会话里执行，CLI 里黑名单词/称呼红线/超长句/独白堆积/比喻词密度全部漏网。
4. **AI 味不可度量**：没有分数，「像不像人写的」全凭手感，1.6 的去 AI pass 无验收标尺。
5. **评分不拦截**：四维评分（EVALUATOR_RUBRIC）只打印不 gate，低分章节照常存盘覆盖。

本 feature 让质量**被度量**（维度分 + AI 味分）、**被机械拦截**（checker）、**被门禁**（存盘前统一判定），并让打回**保住好稿**（fixer 修复式）。

## 2. 术语

- **流水线**：`agent._run_loop` 按 `state.next_agent` 驱动的角色状态机，现为 writer -> polisher -> reviewer。
- **checker**：新角色。polisher 之后、reviewer 之前的纯代码机械检查，零 LLM 调用。
- **fixer**：新角色。打回后的修复者--按结构化意见只改问题处，不整章重写。
- **结构化 issue**：`{quote, problem, fix}` 三元组--引用原文句子、说明问题（含所属维度/规则）、给出改法。reviewer 与 checker 的打回意见统一为此格式。
- **规则文件**：`NOVEL_DIR` 下的单一 JSON（命名见 design，推荐 `质量规则.json`），承载词表与阈值，与 0.2 的写作铁律.md 分开。
- **AI 味浓度分**：0-100 的确定性统计分数，越高越像 AI 写的。
- **基准语料**：AI 味分与句长/词频偏移的参照系 = exemplar 全量 + 人工正文目录（可配）。
- **门禁**：存盘前的统一拦截判定。eval 门禁 = 四维评分的整体加权分低于阈值。
- **EARS**：`当 <条件> 时，系统应 <行为>` 的验收条目格式。

## 3. 验收标准（EARS）

### 3.1 审核维度化（1.1）

- **A1** 当 reviewer 正常返回可解析 JSON 时，返回体应包含 `scores` 对象：八个维度（人物一致性、文风一致性、剧情连贯性、时间线一致性、环境一致性、伏笔一致性、比喻密度、视角越界）各一个 1-5 整数分。后两维为语义级判断（机械检查做不到的，归 reviewer 承载）。
- **A2** 当 reviewer 报告问题时，每个 issue 应为结构化对象（quote 引用原文句子 / problem 说明问题并标注所属维度 / fix 给出建议改法），不再是无定位的纯文字。
- **A3** 当 reviewer 打回时，feedback 应携带维度信息指路（如「文风问题=只改表达不动剧情」）；但不按维度路由到不同 agent（ROADMAP 1.1 明确不做）。
- **A4** 当 reviewer 步骤完成时，维度分与结构化问题应存入 `PipelineState`（新字段，命名见 design）并随 run record 落盘（steps 与 final_state 可见，replay 可查）。
- **A5** 当调用 `parse_review` 时，其签名与返回语义应保持不变（既有调用方与测试零改动）；结构化富解析经新增函数（推荐 `parse_review_full`）返回完整对象。
- **A6** 当 reviewer 返回旧 schema（无 `scores`、issues 为字符串数组）时，系统应照常工作：分数缺省为空、意见按现状折入文本，打回按 pass/reason 既有语义走（FakeLLM 旧脚本与旧模型输出不破）。
- **A7** 当 `harness.run_tests` 执行时，应断言 reviewer 返回含八维分数且各分在 1-5 整数范围。

### 3.2 修复式打回（fixer）

- **A8** 当 reviewer 判不通过时，系统应进入 fixer 做**修复式打回**：保住当前稿件、按意见只改问题处，不再回 writer 从零重写；run/refine/rewrite 三入口的打回目标一致（现有 `_reject_target` 机制随之统一或退役，见 design）。
- **A9** 当 checker 判不通过时，系统应同样进入 fixer（与 reviewer 打回同一路径）。
- **A10** 当 fixer 执行时，系统应按 issues 的 `quote` 在稿件中定位问题所在段落，仅将问题段落及其上下文送 LLM 修复，其余段落逐字节不变（复用 0.4 局部精修的回填管线）。
- **A11** 当一轮打回含多个问题时，系统应合并为一次修复调用（全部问题段 + 各自意见 + 上下文），不逐 issue 逐段多次调用（token 预算意识）。
- **A12** 当任一 quote 无法在稿件中定位（为空或非原文子串）时，系统应降级为整文修复：单次 LLM 调用、携带全部意见、要求保内容只改问题处（不做「可定位走段落级 + 不可定位另行处理」的混合协议）。
- **A13** 当 fixer 产出回填后，稿件应重新过 checker（通过后再过 reviewer），形成「修复 -> 复检」闭环。
- **A14** 当 checker 或 reviewer 打回时，两者应共享同一 `review_count` 预算；达到 `max_reviews` 时走现有强制定稿逃生门（警告 + 留痕），不无限循环。
- **A15** 当修复后正文相对修复前字数缩水超过保护线（沿用 0.4 局部精修的标准）时，系统应不接受该次修复、保留修复前稿件并在 log 留痕。

### 3.3 规则硬 gate（checker）

- **A16** 当 polisher 完成后，系统应在 reviewer 之前执行 checker（纯代码、零 LLM 调用），步骤名 `checker` 计入 run record 的 steps。
- **A17** 当稿件含黑名单词（AI 高频词，词表来自规则文件）时，checker 应判不过并输出 issue：引用所在句、指明命中词。
- **A18** 当稿件命中称呼红线（禁用称呼，词表来自规则文件 naming_redlines.forbidden）时，checker 应判不过并输出 issue 指明词句。（「必备称呼缺失」的机械断言明确不做，见 design D10：误伤不可控，「该出现」的意图断言归 intent_words。）
- **A19** 当稿件存在超过配置上限的长句时，checker 应判不过并输出 issue 引用该句。
- **A20** 当稿件连续独白行（连续非对话叙述行）超过配置上限时，checker 应判不过并指出区间。
- **A21** 当稿件比喻标记词密度超过配置阈值时，checker 应判不过并引用命中句子。
- **A22** 当稿件未命中任何已配置规则时，checker 应通过（不误伤正常产出是验收线）。
- **A23** 当规则文件缺失或某规则键缺失时，系统应跳过对应检查（不误伤）；当规则文件存在但非法 JSON 时，系统应在启动时明确报错（fail-fast，不静默放行）。
- **A24** 当 checker 打回时，问题应以与 reviewer 同构的结构化 issue 输出（quote/problem/fix），统一存入 `PipelineState`，供 fixer 消费。

### 3.4 AI 味量化（1.3）

- **A25** 当对文本计算 AI 味浓度分时，系统应产出 0-100 的确定性分数（零 LLM 调用，同输入同输出），越高越像 AI。
- **A26** 当三个组件均可计算时，总分应为黑名单命中率、句长分布偏移、词频偏移三个归一化组件的线性加权（权重在规则文件可配）；词频偏移以字与 bigram 频率计算（不引入分词依赖）。
- **A27** 当基准语料（exemplar 全量 + 人工正文目录，目录可配）充足时，句长与词频偏移以基准为基线；当语料不足时，系统应降级为只用黑名单 + 句长两组件并标记降级（`eval` 输出可见）。
- **A28** 当 `eval` 命令执行时，输出应新增 AI 味浓度一维；当 `compare` 对比记录时，应并列展示双方 AI 味分（按双方 final_chapter 现算，与记录新旧无关；记录缺 final_chapter 时跳过该行）。
- **A29** 当 AI 味分被计算时，默认只做度量与展示，不进入存盘门禁（是否进门禁等 1.6 有数据后再定）。

### 3.5 门禁统一（1.4，与 0.1 同一门禁哲学）

- **A30** 当 `_do_write` 的流水线完成时，评分（evaluate）应移到章节存盘之前执行；门禁不过时章节文件不自动写入（run record 仍正常落盘留痕，弃而不失数据）。
- **A31** 当评分的整体加权分低于配置阈值且门禁启用时，系统应在 REPL 提示人工确认存/弃（确认缝为 cli 模块级函数，可被测试替换），不自动弃稿、不自动存稿（人是兜底）。
- **A32** 当门禁加权时，标题维不参与（权重固定为 0）；其余各维权重与阈值在规则文件中可配。
- **A33** 当 evaluate 未产出分数（返回 None 或缺维）时，系统应跳过门禁判定、不阻断流程（兼容现有测试缝与模型故障路径）。
- **A34** 当产出已经人工确认（reviewer 强制定稿、审稿不可解析的人工确认存稿、refine/rewrite 的 forced 判优分支）时，系统不应叠加 eval 门禁二次拦截：直接存盘（向量库入库与摘要流程不变），评测照常执行留报告，仅跳过门禁判定。
- **A35** 当执行回测（对既有 run 记录模拟门禁）时，系统应输出各阈值的拦截面与误伤统计，用于先回测再定默认阈值上线（ROADMAP 1.4 原文要求）。

### 3.6 兼容与工具

- **A36** 当 `harness.run_tests` 断言规则红线时，断言数据应来自 NOVEL_DIR 规则文件（称呼红线），不再硬编码具体人名；规则缺失时跳过该断言（现状是源码里写死「许风」/「风」，违反宪法 §1 精神）。
- **A37** 当 replay/compare 消费阶段 0 生成的旧 run 记录（无新字段）时，系统应正常工作。

## 4. 非目标（明确不做）

1. **不做 1.5/1.6**：动态文风注入（学人味）与去 AI 润色 pass 归后续 feature `style-loop`。AI 味量化只度量不治疗；「重写后 AI 味分必须下降才接受」的验收闭环属 1.6。
2. **不做按维度路由打回**：维持单一打回目标 fixer，feedback 带维度指路即可（ROADMAP 1.1 已否决）。
3. **语义级判断不进 checker**：这句话是不是好比喻、视角是否越界归 reviewer 维度；checker 只做词法/统计代理。
4. **不引入分词**：词频偏移用字 + bigram，零新依赖（宪法 §5 纯函数可测优先）。
5. **不动模型配置与 max_tokens**（宪法 §2/§4）：fixer 新调用走既有 `writer_llm` 路由，不新增配置面。
6. **不做批量/API 模式的 fail-closed 门禁**：2.2 的低分章去向是彼时的前置设计题；本 feature 门禁只覆盖 REPL 人在环路径。
7. **不收紧分维阈值**：门禁默认整体加权分；「任一维 < 3」等分维收紧待历史数据校准后再议（ROADMAP 1.4 原文）。
8. **不改 `改` 命令的交互行为**：partial.py 管线被复用但对外行为零改动。
9. **不修存量 3 个失败测试**（`test_strip_polisher_meta`、`test_runtime_dir_override`、`test_defaults`）：与本 feature 无关的既有失败，纪律是零新增失败。
10. **不改 RAG 检索策略与索引时机**。

## 5. 宪法对齐表

| 宪法条款 | 约束要点 | 本 feature 的对齐方式 |
|---|---|---|
| §1 项目身份 | 代码仓库零具体小说名 | 词表/称呼红线/阈值全部进 `NOVEL_DIR` 规则文件；`run_tests` 去「许风」硬编码改读规则文件（A36） |
| §2 技术栈 | LLM/embedding/向量库锁定 | 零模型变更；checker 与 AI 味分是纯代码；fixer 走既有 LLMClient |
| §3 存储与路径 | 小说数据在仓库外 `NOVEL_DIR` | 规则文件放 `NOVEL_DIR`（新配置项指向，env 命名同现有规范）；run record 仍在 `.agent/runs/` |
| §4 glm-5.2 推理预算 | 短输出 ≥1024、长输出 4096、token 预算意识 | checker 零 LLM 调用；fixer 只传问题段 + 上下文不传整章（A10/A11）；fixer 输出走 4096 档 |
| §5 模块边界 | 依赖注入、agent 不 import cli、纯函数优先、state/memory 不混名 | checker.py 新模块为纯函数；fixer 挂 `NovelAgent`（agents 注册）；结构化解析为模块级纯函数（同 `_strip_polisher_meta` 先例）；门禁确认缝在 cli 模块级 |
| §6 开发流程 | spec-kit 三件套 | 本目录即三件套 |
| §7 验收纪律 | 单测绿、不破基线、严禁后阶段指标前移 | 全部测试用 FakeLLM/FakeRag/monkeypatch 离线注入；AI 味分断言用构造语料（一稿 AI 味重、一稿仿人写）验证区分度，不依赖真实模型 |
