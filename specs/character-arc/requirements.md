## 1. 背景与问题

阶段 3.2 规划原文：「分析已有正文的角色状态变化曲线，写新章前提示『该角色当前弧光
阶段』，防人设漂移。」定性：伏笔丢失是结构问题（3.1），人设漂移同样是结构问题--
第 5 章坚定的复仇者到第 15 章无铺垫地心软，读者立刻出戏；表面看是文笔问题，根子上
是 writer 每章都在「凭静态设定卡 + 前文检索」猜角色现状。

现状缺口：

1. **字段是死数据**：`WorkingMemory.character_states: dict` 存在且随
   working_memory.json 持久化，`snapshot()` 也把它注入了 writer/polisher/reviewer 的
   working_context（渲染为 `角色状态：{...}` 原样 dict），但**没有任何代码往里写**--
   永远空 dict，注入的是一句空话。
2. **动态状态无防线**：RAG 检索的人物设定文件是**静态人设卡**（角色是谁），角色
   **走到哪了**（本章结束时的目标/信念/立场）没有任何通道进 writer 上下文。
3. **弧光曲线无处可看**：角色从第 3 章「蒙冤受屈」到第 12 章「决心动摇」走了什么
   路径，全靠人脑记；`状态` 命令的「角色状态」行因此也永远为空。

本 feature 补上**状态抽取回路 + 写前注入 + 人工修正缝**三件事，让字段活起来。
结构上完全对标 3.1 foreshadow（写后旁挂回路 + REPL 命令），模式已验证。

## 2. 术语

- **角色弧光（character arc）**：角色随剧情推进的目标/冲突/信念变化轨迹。参考资产：
  `docs/spec/ddd-modeling.md` 的 CharacterArcStage（章号+目标+冲突+信念+证据）与
  `docs/spec/technical-spec.md` 3.2.1 CharacterArcPlanner（Java 侧仅 5 行占位接口
  未实现，设计文档完整；本 feature 取其数据模型、弃 evidence 字段）。
- **弧光阶段（stage）**：角色当前所处阶段的一句话自包含描述（如「复仇决心初动摇，
  开始怀疑代价是否值得」）。
- **状态条目**：一个角色的完整弧光记录 = 当前阶段 + 目标 + 冲突 + 信念 + 更新章号 +
  历史阶段列表（只记变化点）。
- **抽取（extraction）**：一章定稿后，用一次 LLM 调用完成「更新出场角色状态 + 发现
  新角色 + 判定阶段是否实质变化」三件事。
- **EARS**：`当 <条件> 时，系统应 <行为>` 的验收条目格式。

## 3. 验收标准（EARS）

### 3.1 抽取回路

- **C1** 当一章定稿存盘（`_write_one` 既有写后链路，伏笔抽取之后）时，系统应发起
  一次抽取调用：输入 = 本章正文 + 既有角色状态清单（全量），输出 = 出场主要角色
  各自的最新状态（阶段/目标/冲突/信念）+ 阶段是否实质变化的标记。
- **C2** 当抽取调用成功且返回可解析时，系统应：清单内角色按回报覆盖当前状态，
  清单外角色作为新角色加入；被标记「阶段实质变化」的角色把新阶段连同本章章号追加
  进历史列表；随 `save_working_memory` 落盘（批量模式自然继承，章间连续性零新逻辑）。
- **C3** 当抽取调用失败/返回不可解析时，系统应**不更新角色状态**（宁缺勿错：错误的
  状态会污染后续所有章的 prompt，比空着更糟），打印一句跳过原因；**既有写后链路
  （进度指针/摘要/伏笔/工作记忆落盘）不受影响**，不阻断写作主流程。
- **C4** 当抽取发生（无论成败）时，run record 应留痕：成功记各角色更新结果与阶段
  变化名单，失败记 `{"error": 原因}`（replay 必须能分清「这章没动角色状态」与
  「抽取挂了」）；留痕为顶层 `arc` 键（对齐 `foreshadow`/`exemplar_route` 先例），
  且应实际落盘（抽取后补写一次 record，同 run_id 覆盖）。
- **C5** 当构造抽取 prompt 时，阶段描述应要求**自包含**（一句话说清「角色现在处于
  什么心理/立场状态」，不依赖上下文也能看懂），且单章回报角色数有软上限（默认 6，
  防输出截断与龙套灌水）；模型返回超限时**全收不截断**（截断会丢真主角）。
- **C15** 当同一章号被重写（如 `写第5章` 跑两次）时，抽取结果应**覆盖**该章旧痕迹
  （历史列表中 `chapter == num` 的条目先清，当前状态按新正文重抽覆盖），不产生
  「同一章两个阶段」的脏曲线；守卫：任务串解析不出章号（`num` 为 None，如「写一段
  番外」）时**不清洗历史只更新状态**（否则无章号历史条目会被一次抹掉）。

### 3.2 结构与注入

- **C6** 当角色状态被结构化时，条目应为
  `{"stage", "goal", "conflict", "belief", "chapter", "history": [{"chapter", "stage"}]}`
  （history 按章升序、只记阶段变化点，护栏上限 20 条、超出丢最老）；旧
  working_memory.json 的 `character_states` 恒为 `{}`（字段从未被写过），**天然无
  迁移**；load 对脏条目（非 dict / 缺 stage）丢弃不拒载。
- **C7** 当 `snapshot()` 渲染角色状态时，应从现状的 `角色状态：{dict 原样}` 升级为
  分节渲染（每角色一行：名字 + 更新章 + 阶段 + 目标 + 信念，紧凑分隔），并附一句
  指令性文案（「写作时保持各角色当前阶段与人设连续，不可无故突变」）；状态为空时
  整块不占位；三角色（writer/polisher/reviewer）经 working_context 拿到同一份，
  不窄化不扩面。
- **C8** 当跟踪角色超过注入护栏上限（可配，默认 8）时，prompt 快照应只含最近更新
  的 N 个角色并标注总数；`状态`/`角色` 命令仍显示全量（截断只作用于 prompt 注入）。

### 3.3 人工修正缝

- **C9** 当用户执行 `角色` 命令时，系统应列出全部跟踪角色（名字、更新章、阶段、
  目标/冲突/信念、历史变化数）；`角色 删 <名字>` 停止跟踪（直接移除，不归档--
  角色状态是快照不是线索，角色再出场会被重新发现）；`角色 改 <名字> <新阶段>`
  人工修正当前阶段（更新章取当前章）。未配置 NOVEL_DIR 时应报错而非崩（require 校验）。
- **C10** 当 LLM 抽取有误（阶段判错/龙套入库/主角漏报）时，用户应能经 C9 的命令
  修正，修正后随 working_memory.json 落盘，下章生效（下章抽取的输入清单含修正后
  状态，模型在其基础上演进）。

### 3.4 配置与预算

- **C11** 抽取调用应走主 LLM（判定类，同审稿/摘要/伏笔侧），温度独立可配
  （`NOVEL_ARC_TEMPERATURE`，默认 0.2），max_tokens = 2048（宪法 §4：推理模型思考
  计入预算，6 角色 × 4 字段的 JSON 比伏笔描述更长）。
- **C12** 当 `NOVEL_ARC=0` 时，抽取回路整体禁用，写作行为回到本 feature 前现状；
  快照新格式与人工命令保留（开关只关回路，不关基础设施）。
- **C13** 当批量连写时，预算提示口径应含弧光抽取（每章约 8-11 次 LLM 调用）。
- **C14** 当 replay/compare 消费旧 run 记录（无 arc 键）与旧 working_memory.json
  （character_states 为空 dict）时，系统应正常工作。
