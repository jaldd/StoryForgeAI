# 阶段 3.1：伏笔自动追踪（foreshadow）- 需求

> 需求来源：阶段 3.1 规划条目（长线记忆第一步）与开放问题 4（伏笔追踪独立成小 feature，已拍板）。
> 最高约束：`.specify/memory/constitution.md`。
> 现状证据与详细设计见同目录 `design.md`；任务分解见 `tasks.md`。
> 前置依赖：无新外部依赖；消费既有 `WorkingMemory.unresolved_foreshadowing` 字段
> （已存在但无自动更新通道）与 `_write_one` 写后处理链（摘要/工作记忆/入库）。
> 条目编号用 F 系列（A/B/T 已被 quality-gate/style-loop/throughput 需求占用，避免跨 feature 撞号）。

## 1. 背景与问题

阶段 3.1 规划原文：「每写完一章，LLM 抽取本章埋下的伏笔更新 unresolved 列表；writer prompt
注入'待回收伏笔'提示；回收了则自动出列。」并把此项定性为**结构性刚需**--伏笔丢失是结构
问题，AI 味是表面问题。

现状缺口：

1. **字段是死数据**：`WorkingMemory.unresolved_foreshadowing: List[str]` 存在且随
   working_memory.json 持久化，`snapshot()` 也把它注入了 writer/polisher/reviewer 的
   working_context，但**没有任何代码往里写**（`update_after_write` 的
   `new_foreshadowing` 参数从未被调用方传入）--列表永远为空。
2. **伏笔全靠人脑记**：多章连写（尤其 2.2 批量模式）下，第 5 章埋的线到第 12 章忘收，
   只有读者发现时才知道；`状态` 命令的「未回收伏笔」行因此也永远为空。
3. **无回收判定通道**：即使手动补录了伏笔，也没有「本章回收了它」的出列机制，
   列表只增不减，注入 prompt 的噪音单调上升。

本 feature 补上**抽取回路 + 回收出列 + 人工修正缝**三件事，让字段活起来。

## 2. 术语

- **伏笔（foreshadowing）**：本章正文埋下、尚未在后续剧情中兑现的线索（物件、承诺、
  异常、未解之谜等）。一条伏笔 = 一句自包含描述（不依赖上下文也能看懂）。
- **回收（resolved）**：伏笔在后续章节正文中被兑现/揭晓。回收即从 unresolved 出列、
  移入已回收归档。
- **抽取（extraction）**：一章定稿后，用一次 LLM 调用同时完成「找新伏笔」与「判旧伏笔
  是否被本章回收」两件事。
- **编号协议**：给 LLM 的既有伏笔清单带稳定编号，回收以编号回报（不做文本模糊匹配）。
- **EARS**：`当 <条件> 时，系统应 <行为>` 的验收条目格式。

## 3. 验收标准（EARS）

### 3.1 抽取回路

- **F1** 当一章定稿存盘（`_write_one` 既有写后链路）时，系统应发起一次抽取调用：
  输入 = 本章正文 + 带编号的当前未回收伏笔清单，输出 = 新伏笔列表 + 已回收伏笔编号列表。
- **F2** 当抽取调用成功且返回可解析时，系统应：新伏笔（去重后）追加进
  `unresolved_foreshadowing`（记录埋设章号），被回收的按编号出列并归档，随
  `save_working_memory` 落盘（批量模式自然继承，章间连续性零新逻辑）。
- **F3** 当抽取调用失败/返回不可解析时，系统应**不更新伏笔列表**（宁缺勿错：错误的新增
  会污染后续所有章的 prompt，错误的出列会丢伏笔），打印一句跳过原因；**既有写后链路
  （进度指针/摘要/工作记忆落盘）不受影响**，不阻断写作主流程。
- **F4** 当抽取发生（无论成败）时，run record 应留痕：成功记本章新增与回收结果，
  失败记 `{"error": 原因}`（replay 必须能分清「这章没埋伏笔」与「抽取挂了」）；
  留痕为顶层 `foreshadow` 键（对齐 `exemplar_route` 先例），且应实际落盘
  （`save_run` 在抽取前已执行过，抽取后须补写一次 record）。
- **F5** 当构造抽取 prompt 时，新伏笔描述应要求**自包含**（一句话说清「什么线索 +
  为什么是悬而未决」），且单章新增条数有软上限（默认 5，防输出截断与灌水）；
  模型返回超限时**全收不截断**（截断会丢真伏笔）。
- **F16** 当同一章号被重写（如 `写第5章` 跑两次）时，抽取结果应**覆盖**该章旧条目
  （先清 `chapter == num` 再追加新），不产生近似重复的累积；两道守卫：任务串解析不出
  章号（`num` 为 None，如「写一段番外」）时**不清洗只追加**（否则旧版 str 兼容数据
  与首章前人工补录的条目--chapter 均为 None--会被一次抹掉）；`伏笔 加` 的人工条目
  （manual 标记）不被覆盖清洗（人工补的线不该被模型重跑抹掉）。

### 3.2 结构与注入

- **F6** 当伏笔条目被结构化（描述 + 埋设章号）时，`load_working_memory` 应兼容读取
   旧版纯字符串列表（`str -> {desc, chapter: None}`），旧数据不丢。
- **F7** 当 `snapshot()` 渲染未回收伏笔时，应带编号与埋设章号，并附一句指令性文案
  （「写作时应考虑推进或回收这些伏笔，不强行回收」）--现状三个角色（writer/polisher/
  reviewer）经 working_context 拿到同一份，不窄化不扩面。
- **F8** 当未回收伏笔超过护栏上限（可配，默认 30）时，注入 prompt 的快照应只含最近
  N 条并保留**原编号**（与全量编号一致，防「截断重排」与 `伏笔` 命令对不上）；
  `状态`/`伏笔` 命令仍显示全量（截断只作用于 prompt 注入）。

### 3.3 人工修正缝

- **F9** 当用户执行 `伏笔` 命令时，系统应列出全部未回收伏笔（编号、埋设章号、描述）；
  `伏笔 删 <编号>` 标记已回收（出列入归档，与模型回收同路径，F15）；
  `伏笔 加 <描述>` 手动补录（埋设章号取当前章，打 manual 标记，F16 守卫）；
  `伏笔 已回收` 查看归档（见 F15）。未配置 NOVEL_DIR 时应报错而非崩（require 校验）。
- **F10** 当 LLM 抽取有误（漏抽/误抽/误判回收）时，用户应能经 F9 的命令修正，
  修正后随 working_memory.json 落盘，下章生效。
- **F15** 当伏笔从清单消失时，系统应将其移入已回收归档（`resolved_foreshadowing`，
  记录回收章号）而非物理删除--模型判定回收与人工 `伏笔 删` 走**同一条归档路径**
  （一切「从清单消失」都可恢复，物理删除暂无通道），误判可从归档人工移回，磁盘可恢复。

### 3.4 配置与预算

- **F11** 抽取调用应走主 LLM（判定类，同审稿/摘要侧），温度独立可配
  （`NOVEL_FORESHADOW_TEMPERATURE`，默认 0.2），max_tokens = 2048
  （宪法 §4：推理模型思考计入预算，30 条判定 + 多条自包含描述，1024 偏紧）。
- **F12** 当 `NOVEL_FORESHADOW=0` 时，抽取回路整体禁用，写作行为回到本 feature 前
  现状；快照新格式与人工补录/展示命令保留（开关只关回路，不关基础设施）。
- **F13** 当批量连写时，预算提示口径应含抽取调用（每章约 7-10 次 LLM 调用）。
- **F14** 当 replay/compare 消费旧 run 记录（无 foreshadow 键）与旧 working_memory.json
  （纯字符串列表）时，系统应正常工作。
- **F17** 当尚未写过任何章（current_chapter 为空）但已有伏笔（人工补录）时，
  `状态` 命令仍应显示伏笔块（现状 snapshot 只在 current_chapter 非空时打印）。
