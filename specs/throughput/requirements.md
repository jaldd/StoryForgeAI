# 阶段 2：吞吐（throughput）- 需求

> 需求来源：阶段 2.1-2.2 规划条目。
> 最高约束：`.specify/memory/constitution.md`。
> 现状证据与详细设计见同目录 `design.md`；任务分解见 `tasks.md`。
> 前置依赖：`specs/quality-gate/`（A 系列）与 `specs/style-loop/`（B 系列）完成态--
> 本 feature 的批量连写消费其门禁（`_gate_ok`/`_gate_confirm`）与 de-AI pass（`_deai_pass`），
> 流式输出消费其思考块清洗纪律（`_strip_think_blocks`）。
> 阶段 1 真车验收（style-loop）由用户执行中，不阻塞本 feature 开发；
> 早期规划「阶段 2 批量开闸前复核一次门禁阈值」归入 quality-gate T12 校准批次，
> 不作为本 feature 开发的阻塞条件。
> 条目编号用 T 系列（A1-A37 quality-gate、B1-B20 style-loop 已占用，T 取 throughput）。
> 修订（2026-08-30）：批量任务来源由「标题模板 + 序数后缀」改为「每章规划文件
>（章纲）驱动」（用户工作流：先在 `NOVEL_DIR/每章.md` 规划每章，再批量写）；
> 序数后缀降级为无章纲时的回落方案。

## 1. 背景与问题

阶段 1 闭环了「质量」，阶段 2 闭环「吞吐」。三个具体痛点：

1. **盲等 30 秒**：writer/polisher 各一次完整调用（约 30 秒/次），全程只看一行
   `⏳ 等待模型响应...`（`llm.py:188`）。跑偏要等整章生成完才看得见，改一次重等 30 秒。
2. **一章一敲**：只能一章一章手敲命令。写 10 章要 10 次
   `写第N章：标题` + 10 次人工盯梢，而章与章之间的全部状态传递
   （工作记忆更新、向量库入库、滚动人工正文窗口推进）其实都是机器可做的。
3. **章纲闲置**：用户的既定工作流是「先规划后写作」--`NOVEL_DIR/每章.md`
   已按「章 | 标题 | 核心事件 | 天气 | 矛盾种子」表格规划好了每章内容，
   但写作命令不认识它：标题要手敲、每章的规划要点（写什么、天气、埋什么种子）
   不进 writer prompt--批量连写若不接上它，等于拿自由发挥对抗已有蓝图。

本 feature 补两块：**流式输出**（2.1，写作过程可见、可中途打断）与
**批量连写**（2.2，章纲驱动的区间命令 + 章间自动编排，默认人在环过目）。

## 2. 术语

- **流式（stream）**：chat 请求带 `stream=True`，网关逐 chunk 返回增量；CLI 边收边打印。
- **增量（delta）**：单个流式 chunk 携带的正文片段（`choices[0].delta.content`）。
- **思考块**：思考模型输出中被思考标签包裹的内部推理文本（含未闭合前缀形态）。
- **每章规划文件（章纲）**：`NOVEL_DIR` 下的 `每章.md`（`NOVEL_CHAPTER_PLAN` 可配），
  markdown 表格逐章记录标题与规划要点（核心事件/天气/矛盾种子等列）。
- **规划要点（plan notes）**：章纲表格中标题列之后的各列内容，按「列名：值」
  渲染后注入 writer prompt 的【本章规划】块。
- **区间命令**：形如 `写第5-10章` 或 `写第5-10章：异乡风起` 的一条命令
  （起止章号 + 可选标题模板）。
- **章间确认**：批量模式下每章完成（存盘后）向用户确认是否继续写下一章。
- **EARS**：`当 <条件> 时，系统应 <行为>` 的验收条目格式。

## 3. 验收标准（EARS）

### 3.1 流式输出（2.1）

- **T1** 当流式启用（`NOVEL_STREAM`，默认 1）且 writer/polisher 发起 chat 调用时，
  系统应以流式请求并经回调边收边打印增量正文；`chat` 的返回值仍为收完并清洗后的
  完整文本，与同一输入的非流式调用语义一致。
- **T2** 当流式增量中混入思考块（完整对或未闭合前缀）时，系统应做增量过滤--
  思考内容不打印；返回文本在收完后仍经既有 `_strip_think_blocks` 收尾清洗
  （打印侧与数据侧双层兜底）。
- **T3** 当流式 chunk 携带 `reasoning_content`（增量思考字段，非 content）时，
  系统应不打印、不计入返回正文（兼容思考型网关两种思考输出位置）。
- **T4** 当流式响应收完但正文为空、`finish_reason=length` 且有 reasoning 输出时，
  系统应沿用思考耗尽翻倍 `max_tokens` 重试（上限 16384；extra 显式配置
  `max_tokens` 不翻倍），且翻倍重试时提示可见。
- **T5** 当流式请求因网络/网关异常中断时，系统应丢弃已收增量、整请求按既有
  指数退避重试（2/4/8/16/32 秒，最后一次不多睡）；temperature 400 锁定机制
  对流式同样生效（锁定后整 client 生效）。
- **T6** 当 reviewer/fixer/评委/摘要/样文路由等非生成调用执行时，系统应不启用
  流式（只有 writer/polisher 走流式；reviewer 是短 JSON 输出，流式无意义）。
- **T7** 当用户在写作命令执行期间（流式输出、评测、存盘等任一阶段）Ctrl-C
  打断时，系统应中止当前写作命令--本章不存盘、不更新工作记忆，REPL 主循环
  不退出（回到 `>>>` 提示符）；既有 `_confirm_unparseable`/`_gate_confirm`
  内 input 的 Ctrl-C 语义不变（保守弃）。
- **T8** 当流式启用时，首个增量到达前应显示等待提示；流式中断重试时应打印
  明确的重试提示（用户能分辨「还在写」与「重试中」）。
- **T9** 当流式输出完成后，既有后处理应不受影响：writer 的 `===` 构思分离、
  polisher 的 `_strip_polisher_meta` 与字数保护、de-AI pass 的 quote 定位。
- **T10** 当 `NOVEL_STREAM=0`（显式关闭）时，系统行为与现状逐字节一致；
  流式是 UI 行为，run record 的 schema 与内容不因流式改变（增量不进 record）。

### 3.2 批量连写（2.2，章纲驱动）

**任务来源（章纲消费）**

- **T11** 当用户输入区间命令（`写第5-10章`，标题可省略）时，系统应解析出
  起止章号，并从每章规划文件查得区间内每章的标题与规划要点，逐章构造任务
  `写第N章：{章纲标题}` 顺序连写。
- **T12** 当某章任务确定（单章或批量）且章纲中存在该章条目时，系统应把该章
  规划要点以【本章规划】块注入 writer 的 user prompt（写作依据，防自由发挥跑偏）；
  该块应进入 run record（replay 可见当时按什么规划写的）。
- **T13** 当区间命令显式给出标题模板（`写第5-10章：异乡风起`）时，标题以
  命令为准（模板 + 中文序数后缀，（一）（二）…）；章纲仍存在该章时规划要点
  照常注入（显式标题只赢标题，不豁免规划）。
- **T14** 当章纲未配置（`NOVEL_CHAPTER_PLAN` 留空或文件不存在）时，区间命令
  **必须**显式给标题模板（走 T13 回落），单章命令必须带标题--行为与现状一致；
  章纲存在但区间内缺某章且命令未给标题时，系统应报错列出缺失章号，
  不发起任何 LLM 调用。
- **T15** 当单章命令省略标题（`写第5章`）且章纲存在该章时，系统应从章纲取
  标题与规划要点完成本次写作（章纲对单章命令同样生效）。
- **T16** 当系统解析章纲时，应兼容列头变体（`标题`/`暂定标题`）与多表格分卷
  （全文件所有表格合并为一个章号 -> 条目的映射，纯函数可测）。

**编排与中断**

- **T17** 当批量执行时，每章应完整走既有单章流程（构建 agent -> 流水线 ->
  de-AI pass -> 评测 -> 门禁 -> 存盘 -> 入库 -> 工作记忆更新）--
  批量是编排层，不改单章语义；章间应重建 agent（工作记忆/检索/样文路由取最新状态）。
- **T18** 当一章完成且还有后续章节时（默认模式），系统应章间确认（继续写下一章？
  y/n）；答 n 或 EOF 时优雅停止，已完成章节全部保留。
- **T19** 当 `--auto` 模式下某章门禁不过（应答弃即弃）时，系统应**中断批量**：
  该章不存盘（run record 已落）、后续章节不写、打印明确的中断原因与进度。
  低分章不隔离、不跳过（fail-closed；隔离方案见 design 备选，无数据不启用）。
- **T20** 当批量中某章创作失败（`agent.run` 抛异常）时，系统应中断批量并打印
  原因，不静默继续写后续章节（防跑偏累积）。
- **T21** 当批量正常推进时，工作记忆 `current_chapter` 应随每章保存连续递增，
  每章正文入向量库（第 N+1 章构建时检索得到第 N 章）。
- **T22** 当用户在批量执行中 Ctrl-C 打断时，系统应停止后续章节、已完成章节
  保留、REPL 不崩（与 T7 同语义，作用域扩到整个批量循环）。
- **T23** 当区间非法（起 > 止、跨度超上限 `NOVEL_BATCH_MAX`、章号非正整数）时，
  系统应报错并提示用法，不发起任何 LLM 调用。
- **T24** 当批量连写启动时，系统应打印预算提示（总章数、每章约 6-9 次 LLM 调用
  的量级提示），符合 token 预算意识（早期规划横切约束）。
- **T25** 当区间只含一章（如 `写第5-5章`）时，系统应退化为普通单章写；
  非区间写命令（`写第5章：标题`）行为与现状零变化（章纲注入除外，
  见 T12--既有命令的增量增强，标题仍以命令为准）。

### 3.3 兼容与预算

- **T26** 当新配置缺失时：`NOVEL_STREAM` 缺省 = 1（流式默认开）；
  `NOVEL_BATCH_MAX` 缺省 = 10；`NOVEL_CHAPTER_PLAN` 缺省 = `每章.md`
  （文件不存在视同未配置，T14 回落）。
- **T27** 当批量与单章执行时，两者应共用同一条单章代码路径（单章命令是批量
  的退化形态），单章命令除章纲注入（T12/T15）外零行为变化。
- **T28** 当用户查看帮助时，`help` 输出与 `.env copy.example` 应覆盖新命令
  （区间写、`--auto`）、新配置与章纲工作流说明（可发现性，Z7 哲学）。
- **T29** 当全量测试执行时，`cli/` 下 `python -m pytest tests/ -q` 应保持
  397 passed / 0 failed / 1 deselected 基线之上零新增失败（离线，FakeLLM/
  FakeRag/monkeypatch，不烧真实 token）。

## 4. 非目标（明确不做）

1. **reviewer/评委等非生成调用不开流式**：短 JSON 输出流式无收益（T6 刹边界）。
2. **不做中断续传**：Ctrl-C 打断的章从头重写（不缓存半章续写）；run record
   语义是「完成态留痕」，半章 record 无消费方。
3. **不做低分章隔离待审清单**：早期规划的前置设计题，本 feature 拍板为
   中断（fail-closed）；隔离需要「隔离章是否参与后续连续性」的额外设计，
   等批量真车数据说话后另议（design 备选存档）。
4. **不做并行写作**：章间有严格状态依赖（前文检索/工作记忆），并行必错；
   顺序连写是语义约束不是性能缺陷。
5. **章纲只读消费**：不写回、不编辑、不校验规划要点与既有正文的一致性
   （如已写章节与章纲冲突）；生成/修订章纲归阶段 3.3 planner。
6. **规划要点不进 polisher/reviewer prompt**（P0 范围）：writer 按规划产出，
   构思（outline）已沿 0.8 既有链路喂 polisher/reviewer；直接把规划喂 reviewer
   作验收基准留待数据说话（design P1 存档）。
7. **不引入 CLI 框架**：区间解析是纯函数 + 既有 startswith 分发，宪法 §2。
8. **不动存储路径与 record schema 语义**：`正文/AI生成/`、`.agent/` 约定不动
   （宪法 §3）；`PipelineState` 新增 `plan` 字段是 asdict 自然扩展，replay/
   compare 对未知键零崩溃（A37 纪律）；流式不进 record，批量每章一个独立
   record（与单章同构）。
9. **不做跨进程批处理/定时任务**：批量是 REPL 内的一条命令，不是守护进程。
10. **不修既有 3 个存量失败测试**（style-loop 验收口径遗留）：纪律是零新增。

## 5. 宪法对齐表

| 宪法条款 | 约束要点 | 本 feature 的对齐方式 |
|---|---|---|
| §1 项目身份 | 代码仓库零具体小说名 | 章纲是 `NOVEL_DIR` 内容、路径经 `NOVEL_CHAPTER_PLAN` 配置；解析器只认通用表格结构（章号/标题列头），零小说内容进代码；新配置全走 `.env` |
| §2 技术栈 | 内置 input()+while，零新框架/新依赖 | 流式用 openai SDK 既有 `stream=True`（依赖已在）；区间/章纲解析纯函数正则 |
| §3 存储与路径 | 小说数据在仓库外 NOVEL_DIR | 章纲从 NOVEL_DIR 读；批量落盘走既有 save_chapter（`正文/AI生成/`）与 `.agent/runs/`，路径零新增 |
| §4 glm-5.2 推理预算 | 长 4096、思考翻倍、token 预算意识 | 流式沿用翻倍/上限 16384 纪律（T4）；批量打印预算提示 + `NOVEL_BATCH_MAX` 硬上限（T23/T24）；规划要点注入是一次性输入成本，替代的是「无方向重写」的更大浪费 |
| §5 模块边界 | 依赖注入、纯函数优先、agent 不 import cli | `on_delta` 回调注入（llm 不 print 增量）；`parse_chapter_range`/`parse_chapter_plan` 纯函数入 storage；`stream`/`plan` 是注入参数；确认缝复用 `_gate_confirm`（cli 模块级） |
| §6 开发流程 | spec-kit 三件套 | 本目录即三件套 |
| §7 验收纪律 | 单测绿、不破基线、离线可测 | 流式用 FakeStreamIterable 注入假网关；章纲解析用构造 markdown 断言；批量用 FakeAgent/monkeypatch 全离线（T29） |
