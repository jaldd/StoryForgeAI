## 阶段 1：读懂现有架构（1-2 天）

### 学习目标（对应 xuqiu.md 知识点）
- ✅ Agent 核心组件（Chain/Agent/Memory/Tools）
- ✅ Chain 和 Agent 的区别
- ✅ LangChain 框架基础

### 要读的代码（按顺序）

#### Step 1.1 理解六边形架构（端口适配器）
先看模块依赖关系：
```
bootstrap → api + infrastructure + cli → application → domain
```

读这些文件，理解分层：
- `domain/src/main/java/ai/storyforge/domain/model/Document.java` — 领域实体
- `domain/src/main/java/ai/storyforge/domain/repository/DocumentRepository.java` — 仓储接口（端口）
- `application/src/main/java/ai/storyforge/application/port/inbound/WritingAgentUseCase.java` — 入站端口
- `application/src/main/java/ai/storyforge/application/port/outbound/ModelGateway.java` — 出站端口
- `infrastructure/src/main/java/ai/storyforge/infrastructure/llm/ZhipuModelAdapter.java` — 出站适配器
- `api/src/main/java/ai/storyforge/api/controller/ProjectController.java` — 入站适配器

**关键理解**：
- `domain` 零依赖，定义核心业务概念
- `application` 定义"用例"（入站端口）和"技术接口"（出站端口）
- `infrastructure` 实现出站端口（LLM、数据库、MCP）
- `api` 实现入站端口（REST 控制器）

**对照 Java Spring**：
| 六边形概念 | Spring 对应 | 你熟悉的 |
|-----------|------------|---------|
| 入站端口 | Service 接口 | `@Service` |
| 出站端口 | Repository 接口 | `@Repository` 接口 |
| 入站适配器 | Controller | `@RestController` |
| 出站适配器 | Repository 实现 | JPA 实现 |

#### Step 1.2 理解 Agent 核心链路
读 `WritingAgentService.java`（重点！）：
```
用户消息 → buildContext() → buildFullPrompt() → modelGateway.chat() → 返回
```

**对应 xuqiu.md 的概念**：
- `buildContext()` = 简单版 Memory（把章节/角色/世界观塞进 Prompt）
- `buildFullPrompt()` = 简单版 Prompt 工程
- `modelGateway.chat()` = LLM 调用
- 整个 `WritingAgentService` = 简单版 Agent（但没有 ReAct、没有工具）

**关键认知（Chain vs Agent）**：
- **Chain** = 固定流程（输入 → 处理 → 输出），像流水线
- **Agent** = 能自主决策（决定调什么工具、调几次），像有脑子的人
- 你现在的 `WritingAgentService` 其实是 Chain，不是真正的 Agent（因为它不会自己决定调工具）

#### Step 1.3 理解 LLM 适配器
读 `ZhipuModelAdapter.java`：
- 看 `chat()` 方法：构造 `ChatMessage` → 调智谱 API → 返回内容
- 看 `chatStream()` 方法：用 Reactor `Sinks` 把同步流式 API 转成 `Flux<String>`

**对应 xuqiu.md 的概念**：
- LangChain 的 LLM 抽象 = `ModelGateway` 接口（对应 JDBC 的 Driver 接口）
- `ZhipuModelAdapter` = 具体驱动（对应 MySQL Driver）
- 换模型只需要换适配器，不动业务代码（这就是端口适配器模式的价值）

### 动手任务
1. 画一张架构图（手画或用工具），标出一次聊天的完整调用链
2. 在 `WritingAgentService.chat()` 第一行加日志，打印 `context` 和 `fullPrompt`，看实际发给 LLM 的是什么
3. 尝试加一个新的 `ModelGateway` 实现（比如一个 `MockModelGateway`，返回固定字符串），用 `@Profile("mock")` 切换

### 验收标准
- [ ] 能画出六边形架构图，标清端口和适配器
- [ ] 能讲清楚 Chain 和 Agent 的区别（你现在是 Chain）
- [ ] 能讲清楚 `ModelGateway` 接口为什么这么设计（换模型不动业务）
- [ ] 能讲清楚 `chatStream` 怎么把同步流式 API 转成 Reactor Flux

### 面试话术
> "项目用六边形架构，domain 层零依赖，application 层定义端口（接口），infrastructure 层实现出站端口。比如 LLM 调用抽象成 `ModelGateway` 接口，智谱、OpenAI 都是适配器实现，换模型不动业务代码。目前的 `WritingAgentService` 其实是 Chain 不是 Agent——固定流程调用 LLM，没有自主决策和工具调用。后面的阶段会把它升级成真正的 Agent。"

## 阶段 2：Prompt 工程深入（1-2 天）

### 学习目标（对应 xuqiu.md 知识点）
- ✅ Prompt 工程（角色/任务/约束）
- ✅ ReAct 模式（Thought/Action/Observation）

### 要做的事

#### Step 2.1 改造现有 Prompt
当前 `WritingAgentService.buildFullPrompt()` 很简单：
```java
return """
    你是一个专业的小说创作助手。以下是当前小说项目的相关信息：
    %s
    用户的需求是：%s
    请根据上述信息，帮助用户完成创作任务。
    """.formatted(context, userMessage);
```

**问题**：没有角色设定细节、没有约束、没有 ReAct。

**改造任务**：设计一个完整的 Prompt 模板，包含：
1. **角色设定**：你是谁（小说创作大师，擅长xxx）
2. **任务描述**：你要做什么（根据用户需求辅助创作）
3. **约束条件**：保持人物设定一致、剧情连贯、文风统一
4. **输入信息**：当前小说的章节/角色/世界观
5. **输出要求**：格式、长度、风格

参考 `xuqiu.md` 第 155-173 行的 Prompt 设计要求。

#### Step 2.2 实现 Prompt 模板管理
创建一个 `PromptTemplate` 类（或用 LangChain4j 的 `PromptTemplate`）：
```java
// application/src/main/java/ai/storyforge/application/prompt/NovelPromptTemplate.java
public class NovelPromptTemplate {
    public String buildSystemPrompt() { /* 角色设定 */ }
    public String buildContextPrompt(String context) { /* 小说信息 */ }
    public String buildUserPrompt(String userMessage) { /* 用户需求 */ }
    public String buildReActPrompt() { /* ReAct 引导 */ }
}
```

#### Step 2.3 理解并实现 ReAct 模式
**ReAct = Reasoning + Acting**，流程：
```
Thought: 我需要先查一下主角的设定
Action: search_character("李明")
Observation: 李明，28岁，程序员，性格内敛...
Thought: 现在我知道主角性格了，可以开始写
Action: write_chapter("...")
Observation: 章节已写完
Thought: 任务完成
Final Answer: 这是写好的章节...
```

**现在做不到完整 ReAct**（因为还没工具），先做"ReAct 引导 Prompt"：
在 Prompt 里告诉 LLM："请先思考你需要什么信息，再回答"。观察 LLM 输出是否有 Thought 痕迹。

这个阶段的目的是**理解 ReAct 的格式和思想**，真正的 ReAct 循环在阶段 3 实现工具后才能完整跑通。

#### Step 2.4 对比 Java 经验
- Prompt 模板 = Spring 的 View 模板（Thymeleaf）
- 角色设定 = Spring 的 `@Component` 角色定义
- ReAct = 你在工地智能体里讲过的 Thought-Action-Observation

### 动手任务
1. 改造 `WritingAgentService`，用新的 `NovelPromptTemplate`
2. 加一个 `system` 角色消息（目前只有 `user` 消息），对比效果
3. 在 Prompt 里加 ReAct 引导，观察 LLM 输出变化
4. 测试不同 temperature（0.3 vs 0.9）对创作的影响

### 验收标准
- [ ] Prompt 包含完整的角色/任务/约束/输入/输出五要素
- [ ] 能讲清楚 ReAct 模式的 Thought/Action/Observation
- [ ] 能讲清楚 system 消息和 user 消息的区别
- [ ] 能讲清楚 temperature 对生成的影响

### 面试话术
> "Prompt 工程我总结了五要素：角色设定、任务描述、约束条件、输入信息、输出要求。我在项目里把 Prompt 模板抽成单独的类管理。ReAct 模式是 Reasoning + Acting，让 LLM 先思考再行动——Thought 决定调什么工具，Action 执行工具，Observation 接收结果，循环直到完成。这个模式对应到我之前工地智能体里的 Thought-Action-Observation 决策链。"

## 阶段 3：工具系统（Function Calling）（2-3 天）

### 学习目标（对应 xuqiu.md 知识点）
- ✅ Tools/Function Calling
- ✅ Agent 核心能力（从 Chain 升级到 Agent）

### 要做的事

#### Step 3.1 定义工具接口
参考 `xuqiu.md` Step 1 和项目已有的 `docs/novel-agent-architecture.md` 第 131-160 行。

在 `application` 层定义工具接口：
```java
// application/src/main/java/ai/storyforge/application/tool/Tool.java
public interface Tool<I, O> {
    String name();
    String description();  // 告诉 LLM 什么时候用这个工具
    Class<I> inputType();
    O execute(I input);
}
```

**关键理解**：`description()` 是核心——它告诉 LLM "我什么时候该用这个工具"。这就是 xuqiu.md 说的"语义引导"。

#### Step 3.2 实现三个工具
按 `xuqiu.md` 的要求，实现：

1. **SearchCharacterTool** — 查人物设定
   - 当前用假数据（从内存 Map 返回）
   - 阶段 5 会换成 RAG 检索

2. **SearchSceneTool** — 查场景设定
   - 同上

3. **WriteChapterTool** — 写章节
   - 调用 `ModelGateway` 生成章节内容
   - 保存到 `DocumentRepository`

每个工具参考 `xuqiu.md` 第 117-138 行的要求。

#### Step 3.3 实现工具注册表
```java
// application/src/main/java/ai/storyforge/application/tool/ToolRegistry.java
public class ToolRegistry {
    private final Map<String, Tool<?, ?>> tools = new ConcurrentHashMap<>();
    public void register(Tool<?, ?> tool) { ... }
    public Tool<?, ?> get(String name) { ... }
    public List<ToolSchema> getAllSchemas() { ... }  // 给 LLM 看的工具列表
}
```

#### Step 3.4 实现 Function Calling
**这是把 Chain 升级成 Agent 的关键步骤。**

用智谱 GLM 的 Function Calling 能力（或 LangChain4j 的 `@Tool` 注解）：

**方式 A：用 LangChain4j 的 AiServices + @Tool**
```java
public interface WritingAgent {
    @SystemMessage("你是小说创作助手...")
    String chat(@UserMessage String message, @MemoryId String sessionId);
}

// 工具类
public class NovelTools {
    @Tool("根据关键词查询人物设定")
    public String searchCharacter(String keyword) { ... }

    @Tool("根据关键词查询场景设定")
    public String searchScene(String keyword) { ... }

    @Tool("写一个章节")
    public String writeChapter(String content) { ... }
}
```

**方式 B：手动实现 ReAct 循环**（更利于理解原理）
1. 把工具 schema 发给 LLM
2. LLM 返回要调的工具 + 参数
3. 执行工具，把结果拼回 Prompt
4. 再问 LLM，直到它说"完成"

**建议两种都试**：先试 A（感受框架能力），再试 B（理解原理）。

#### Step 3.5 对比 Java 经验
- LangChain4j 的 `@Tool` = Spring 的 `@Bean`（自动注册）
- `ToolRegistry` = Spring 的 `ApplicationContext`（管理 Bean）
- Function Calling = Java 的反射动态调用 + LLM 决策

### 动手任务
1. 实现三个工具 + 注册表
2. 用方式 A（LangChain4j AiServices）让 Agent 能调工具
3. 打印 Agent 的 Thought/Action/Observation 过程
4. 用方式 B 手动实现一次 ReAct 循环（理解原理）
5. 测试：让 Agent "写一章主角出差遇到问题的剧情"，观察它是否先查设定再写

### 验收标准
- [ ] 三个工具能定义出来，description 清晰
- [ ] Agent 能自主决定调哪个工具
- [ ] 能看到 Thought/Action/Observation 过程
- [ ] 能讲清楚 Function Calling 的原理（LLM 返回工具名+参数，代码执行）
- [ ] 能讲清楚 Chain 和 Agent 的区别（Agent 能自主调工具）

### 面试话术
> "我用 LangChain4j 的 @Tool 注解实现了 Function Calling。工具的核心是 description——它告诉 LLM 什么时候用这个工具，这就是语义引导。Agent 和 Chain 的区别：Chain 是固定流程，Agent 能根据 LLM 的决策动态调工具。我实现了 ReAct 循环：LLM 返回要调的工具和参数，代码执行后把结果拼回 Prompt，再问 LLM，循环直到完成。这对应到我之前做的 MCP Server——本质都是工具协议层。"

## 阶段 4：记忆系统（Memory）（2 天）

### 学习目标（对应 xuqiu.md 知识点）
- ✅ Memory（短期 vs 长期）

### 要做的事

#### Step 4.1 理解当前"假 Memory"
现在 `WritingAgentService.buildContext()` 每次都把所有章节/角色/世界观塞进 Prompt——这是"全量上下文"，不是真正的 Memory。
**问题**：
1. 不记得对话历史（你上一句说了啥，下一句它不知道）
2. 全量塞会超 Token 限制
3. 没有"工作记忆"（当前写到哪了、角色现在啥状态）

#### Step 4.2 实现短期记忆（对话历史）
参考 `xuqiu.md` 第 155-173 行和 `docs/novel-agent-architecture.md` 第 263-300 行。

用 LangChain4j 的 `ChatMemory`：
```java
// 方式 A：用框架
ChatMemory memory = MessageWindowChatMemory.withMaxMessages(20);

// 方式 B：自己实现（理解原理）
public class ConversationMemory {
    private final Map<String, List<ChatMessage>> histories = new ConcurrentHashMap<>();
    public void add(String sessionId, ChatMessage msg) { ... }
    public List<ChatMessage> getRecent(String sessionId, int n) { ... }
}
```

**关键理解**：
- 短期记忆 = 最近 N 轮对话（Token 预算滑动窗口）
- 超过窗口的旧对话要"摘要补偿"（用 LLM 总结）

#### Step 4.3 实现工作记忆（小说状态）
参考架构文档第 269 行："工作记忆：当前项目态（角色状态、章节目标、未回收伏笔）"。

设计一个 `NovelState`：
```java
public record NovelState(
    String currentChapter,      // 当前写到第几章
    Map<String, String> characterStates,  // 角色当前状态
    List<String> unresolvedForeshadowing, // 未回收的伏笔
    String lastPlotPoint        // 上一个剧情点
) {}
```

存到数据库或 Redis（先用内存 Map）。

#### Step 4.4 实现长期记忆（摘要）
每次对话结束后，用 LLM 把对话总结成一段摘要，存起来：
```java
public class SummaryMemory {
    public void summarize(String sessionId, List<ChatMessage> messages) {
        String summary = modelGateway.chat("请总结以下对话：" + messages);
        store.save(sessionId, summary);
    }
}
```

#### Step 4.5 三层记忆整合
最终结构（参考架构文档第 279-299 行）：
- **短期记忆**：最近 20 轮对话原文
- **长期记忆**：历史对话的摘要 + 向量检索（阶段 5 实现）
- **工作记忆**：当前小说状态（角色/章节/伏笔）

`MemoryManager.buildContext()` 把三层合并成最终上下文。

#### Step 4.6 对比 Java 经验
- 短期记忆 = HTTP Session（有期限）
- 工作记忆 = 应用状态（当前任务上下文）
- 长期记忆 = 数据库（持久化）

### 动手任务
1. 给 `WritingAgentService` 加对话历史（短期记忆）
2. 实现 `NovelState` 工作记忆，每次写完章节更新状态
3. 实现摘要记忆，超过 20 轮自动总结
4. 测试：连续聊 5 轮，确认 Agent 记得前面说过的话

### 验收标准
- [ ] Agent 能记住对话历史
- [ ] 能讲清楚短期/长期/工作记忆的区别
- [ ] 能讲清楚 Token 预算滑动窗口

## 阶段 5：RAG（向量检索）（3-4 天）

### 学习目标（对应 xuqiu.md 知识点）
- ✅ RAG 架构（Embedding → 检索 → Rerank → 生成）
- ✅ Embedding 原理

- ✅ Chunking 策略
- ✅ Hybrid Search（向量 + 关键词）
- ✅ Rerank（重排）
- ✅ RAG 解决幻觉

### 要做的事

#### Step 5.1 理解为什么需要 RAG
**当前问题**：`buildContext()` 把所有设定全塞进 Prompt。
- 小说长了会超 Token 限制
- LLM 看太多信息会"抓不住重点"
- 容易编造（幻觉）——不基于设定乱写

**RAG 解决方案**：只检索最相关的设定片段塞进 Prompt。

#### Step 5.2 实现 Embedding（向量化）
项目已有 `EmbeddingClient` 接口（在 application/port/outbound），但没实现。

用智谱的 Embedding API（或 LangChain4j 的 `EmbeddingModel`）：
```java
// infrastructure/src/main/java/ai/storyforge/infrastructure/rag/ZhipuEmbeddingClient.java
@Component
public class ZhipuEmbeddingClient implements EmbeddingClient {
    @Override
    public float[] embed(String text) {
        // 调智谱 embedding-2 模型，把文本转成 1024 维向量
    }
}
```

**关键理解**：Embedding = 把文本变成一串数字（向量），语义相近的文本向量距离近。

#### Step 5.3 实现 Chunking（分块）
参考 `xuqiu.md` 第 270 行："按句子分，每块 200-500 字"。

实现分块策略：
```java
public class DocumentChunker {
    public List<DocChunk> chunk(Document doc) {
        // 按句子/段落分，每块 200-500 字，有重叠
    }
}
```

**关键理解**：
- 为什么要分块：整篇文档太长，Embedding 效果差，检索粒度粗
- 重叠（overlap）：避免切断语义，比如每块 500 字，重叠 100 字

#### Step 5.4 实现向量存储
项目已有 `VectorStore` 接口，但没实现。

**方式 A：用 pgvector**（项目已加依赖）
- PostgreSQL + pgvector 扩展

**方式 B：用内存版**（简单先跑通）
```java

    public List<DocChunk> search(float[] queryVec, int topK) {
        // 计算余弦相似度，返回 topK
    }
}
```

**建议**：先用方式 B 跑通流程，再用方式 A 上生产。

#### Step 5.5 建知识库

2. Embedding 向量化
3. 存入向量库

public class RagIndexService {
    public void indexProject(String projectId) {
        List<Document> docs = documentRepository.findByProjectId(projectId);
        for (Document doc : docs) {
            List<DocChunk> chunks = chunker.chunk(doc);
            for (DocChunk chunk : chunks) {

#### Step 5.6 实现检索工具
把阶段 3 的 `SearchCharacterTool` 从"假数据"换成 RAG 检索：

#### Step 5.8 实现 Hybrid Search（混合检索）
**为什么需要**：向量检索擅长语义匹配，关键词检索擅长精确匹配，结合更好。

```java
public class HybridSearcher {
    public List<DocChunk> search(String query) {
        List<DocChunk> vectorResults = vectorStore.search(embed(query), 10);
        List<DocChunk> keywordResults = keywordSearch(query, 10);  // 简单的 contains 匹配
        return mergeAndRerank(vectorResults, keywordResults);
    }
}
```

- Rerank = ES 的 rescore

### 要做的事

#### Step 6.1 理解 MultiAgent 架构

1. **Director Agent（导演/Supervisor）**：决定下一步让谁做

#### Step 6.2 定义共享状态（State）

// application/src/main/java/ai/storyforge/application/agent/MultiAgentState.java
public record MultiAgentState(
    String task,           // 用户需求
    String draft,          // 草稿
    String dialogue,       // 润色后的对话
    String feedback,       // 审稿意见

) {}
```

#### Step 6.3 定义四个 Agent（Node）
每个 Agent 是一个函数/方法，输入 State，输出新 State：

public class WriterAgent {

    }
}

public class CharacterAgent {
    public MultiAgentState execute(MultiAgentState state) {

        return state.withDialogue(polished);
    }
}

public class EditorAgent {

        String feedback = modelGateway.chat("审稿：" + state.dialogue());

    }
}
```

#### Step 6.4 实现 Director（Supervisor 路由）
对应 LangGraph 的 `conditional_edges`：

```java
public class DirectorAgent {
    public String decideNext(MultiAgentState state) {
        if (state.draft() == null) return "writer";
        if (state.dialogue() == null) return "character";
        if (state.feedback() == null) return "editor";
        if (feedbackIsGood(state.feedback())) return "end";
        return "writer";  // 重写
    }
}
```

#### Step 6.5 构建 Graph（状态图编排）
用 Spring StateMachine 或自己写一个简单的图执行器：

```java
public class MultiAgentGraph {
    public String run(String task) {
        MultiAgentState state = new MultiAgentState(task, null, null, null, null, START);
        
        while (state.currentStep() != END) {
            String next = director.decideNext(state);
            switch (next) {
                case "writer" -> state = writer.execute(state);
                case "character" -> state = character.execute(state);
                case "editor" -> state = editor.execute(state);
                case "end" -> state = state.withStep(END);
            }
            logStep(state);  // 记录每一步（为阶段 7 回放准备）
        }
        
        return state.finalChapter();
    }
}
```

## 第一块：Claude Code（用工具，不写代码）

### CC-1 环境搭建

- **做什么**：装 Node.js → 装 Claude Code（`npm install -g @anthropic-ai/claude-code`）→ 配 Anthropic API Key（或用 Claude 订阅登录）→ 在 `StoryForgeAI` 目录里跑 `claude` 命令
- **产出**：终端能和 Claude 对话，能让你它读到你项目里的文件
- **算学会**：能对 Claude 说"读一下 docs/修仙不如陪她看云/总纲.md 然后总结"，它真的读到了
- **名词**：API Key、Context（上下文）
- **可能遇到的坑**：Node 版本太老（要 18+）、API Key 没配环境变量、在中国大陆需要处理网络访问

### CC-2 基础使用 + Plan Mode

- **做什么**：让 Claude 帮你读/改文档；按 Shift+Tab 切换到 Plan Mode（先规划再执行）；观察流式输出
- **产出**：用 Claude Code 给你的小说改一段设定
- **算学会**：能讲清 Plan Mode 和普通模式的区别
- **名词**：Prompt、Plan Mode、Streaming
- **可能遇到的坑**：Plan Mode 下它只规划不动手，记得切回正常模式才执行

### CC-3 MCP 实操

- **做什么**：给 Claude Code 接一个现成 MCP server（官方的 filesystem 或 memory），让它通过 MCP 读写文件
- **产出**：Claude 通过 MCP 工具操作你的小说文档
- **算学会**：能讲清 MCP 是干嘛的、和直接读文件有啥区别
- **名词**：MCP、Tool Use
- **可能遇到的坑**：MCP 配置在 `~/.claude.json` 或项目的 `.mcp.json` 里，配错路径不报错只是不生效

### CC-4 Subagent + 自定义 Skill

- **做什么**：体验 Subagent（让子代理独立干一个任务）；写一个针对你小说的 Skill（比如"按文风基准检查一段文字"）
- **产出**：一个能用的小说 Skill
- **算学会**：能讲清 Subagent 和主代理的区别
- **名词**：Subagent、Skill
- **可能遇到的坑**：Skill 是 markdown 文件放在 `.claude/skills/`，描述要具体否则 Claude 不知道何时调用

## 第二块：Python + Claude API（写代码，深入底层）

### PY-1 Python 环境 + 首次 API 调用

- **做什么**：装 Python 3.11+、venv、`pip install anthropic`；写 10 行代码调通 Claude
- **产出**：一个 `hello_claude.py`，跑出来 Claude 回了一句话
- **算学会**：能讲清 messages API 的 system/user 角色
- **名词**：messages API、Token
- **可能遇到的坑**：API Key 要放 `.env` 别提交 git、中国大陆网络访问、messages API 要传 `max_tokens`

### PY-2 Prompt 工程 + 流式

- **做什么**：把 `docs/修仙不如陪她看云/文风基准/1.txt` 做成 system prompt；流式输出一段小说
- **产出**：能按你小说文风生成一段文字
- **算学会**：能讲清 Context Window 限制、为什么要流式
- **名词**：Prompt 工程、Context Window、Streaming
- **可能遇到的坑**：system prompt 太长会挤占 token 预算、流式要处理 chunk 拼接

### PY-3 Tool Use + ReAct

- **做什么**：定义 2-3 个工具（查人物、查章节、写章节），让 Claude 自主决定调哪个
- **产出**：Claude 写一章前会先查设定再写
- **算学会**：能讲清 Function Calling 原理、ReAct 的 Thought-Action-Observation
- **名词**：Tool Use / Function Calling、ReAct
- **可能遇到的坑**：工具的 description 写不清楚 Claude 就不会调、要处理 tool_use 和 tool_result 的来回

### PY-4 Memory 三层

- **做什么**：短期（对话历史）+ 工作记忆（小说状态：角色/章节/伏笔）+ 长期（摘要）
- **产出**：连续聊 5 轮，Claude 记得前面说的
- **算学会**：能讲清三层 Memory 区别、滑动窗口、摘要补偿
- **名词**：短期/工作/长期 Memory
- **可能遇到的坑**：对话历史超过 token 限制要截断、工作记忆要持久化否则重启丢

### PY-5 RAG 检索

- **做什么**：用 Chroma（本地向量库）+ Claude 的 Embedding 或本地模型；把小说设定分块、索引、检索
- **产出**：Claude 写章节时自动检索相关设定
- **算学会**：能讲清 Embedding、Chunking、Rerank、Hybrid Search
- **名词**：RAG、Embedding、Chunking、Rerank
- **可能遇到的坑**：分块太大语义糊、太小丢失上下文；Voyage AI 是 Anthropic 官方 embedding 推荐或用本地 BGE

### PY-6 MultiAgent

- **做什么**：写 Director/Writer/Editor 三个 Agent，Director 调度
- **产出**：一次生成经过"写→润色→审稿"的章节
- **算学会**：能讲清 Supervisor 模式、状态图
- **名词**：MultiAgent、Supervisor、状态图
- **可能遇到的坑**：Agent 之间传状态容易乱、要定义清楚共享 State 结构

### PY-7 Harness + 评测

- **做什么**：运行日志存 JSON、回放、用 LLM 打分、A/B 对比配置
- **产出**：一个能回放、能打分的 Agent 测试台
- **算学会**：能讲清"可测试/可评估/可回放/可比较"
- **名词**：Harness、评测体系
- **可能遇到的坑**：日志要记完整输入输出否则回放不全、打分 prompt 要稳定

## 第三块：对话写小说（不编程，出作品）

### D-1 Brainstorm

- **做什么**：和 Claude 聊情节走向、人物弧光，不急着写正文
- **产出**：一份可用的章节大纲
- **算学会**：能讲清 Brainstorm 就是先发散再收敛
- **名词**：Brainstorm

### D-2 文风对齐

- **做什么**：把你 `docs/修仙不如陪她看云/文风基准/` 的 14 个 txt 做成可复用 prompt 模板
- **产出**：一个能复用的"文风 system prompt"
- **算学会**：能讲清 Prompt 模板的作用
- **名词**：Prompt 模板

### D-3 写正文

- **做什么**：一章章写，对照 `文风基准/` 对密度
- **产出**：至少 3 章可读正文
- **算学会**：能讲清长篇上下文管理（chunk、摘要、状态）
- **名词**：上下文管理
